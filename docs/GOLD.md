## 1. Overview & Meaning of Gold

In the AURORA platform, a **Gold Dataset** represents versioned, reproducible, analysis-ready scientific feature datasets and candidate/anomaly records derived strictly from **Silver Parquet** artifacts.

### Data Layer Separation

```text
Bronze (MinIO `bronze/`)
    Raw FITS products streamed directly from NASA MAST.
    Managed by rolling retention policy (~50 GiB rolling window).

Silver (MinIO `silver/`)
    Deterministic, cleaned, normalized Parquet time-series and cutout data.
    Processed by Rust Preprocessor. Immutable downstream science boundary.

Gold (MinIO `gold/`)
    Derived scientific feature tables, candidate vetting evidence, and ML training sets.
    Generated by Python ML Worker (`python-ml-worker`). Immutable versioned snapshots.
```

## 3. Gold Snapshot Architecture

Gold datasets are organized into **Immutable Snapshots**. There is no single `gold/current.parquet` file that gets repeatedly mutated.

### Storage Layout

```text
gold/
└── snapshots/
    └── <snapshot-id>/
        ├── manifest.json
        ├── candidate-features/    (Added in Phase 5.5)
        │   └── part-0000.parquet
        └── anomaly-features/      (Added in Phase 5.5)
            └── part-0000.parquet
```

### Snapshot Identity Format

Snapshot IDs follow a human-safe deterministic pattern:

```text
gold-v1-<sha256-prefix>
```

Example: `gold-v1-4f72be920841`

---

## 4. Deterministic Identity Derivation Algorithm

To guarantee exact scientific reproducibility across execution runs, `snapshot_id` and `snapshot_fingerprint` are derived strictly from a canonical SHA-256 digest of input identities and version declarations.

### Deterministic Inputs
1. `identity_version`: `"gold-snapshot-id-v1"`
2. `snapshot_type`: `"CANDIDATE"` or `"ANOMALY"`
3. `gold_schema_version`: e.g. `"gold-candidate-v1"`
4. `feature_versions`: e.g. `{"LIGHT_CURVE": "lc-features-v1"}`
5. `catalog_snapshots`: versioned catalog reference map
6. `label_snapshots`: versioned label reference map
7. `inputs`: canonically sorted list of verified `SilverInputRef` items:
   - Sort keys: `(product_kind, source_product_id, processor_version, silver_object_key)`
   - Checked fields per input: `lineage_id`, `source_product_id`, `product_kind`, `silver_object_key`, `silver_sha256`, `silver_schema_version`, `processor_version`, `sample_id`

### Excluded Operational Noise
The following operational/runtime metadata MUST NOT participate in snapshot identity derivation:
- Wall-clock execution time (`created_at`)
- Hostnames, process PIDs, container IDs
- Python `hash()` or random UUIDs (`uuid4()`)
- Worker concurrency counts or MinIO URLs

## 5. Lineage-Driven Silver Discovery

Stage 5 snapshot planning discovers Silver artifacts by querying committed Lineage records (`lineage/v1/`). This guarantees that:
- Only legitimate, preprocessor-verified Silver outputs are included.
- Uncommitted, temporary, or corrupted Silver files are rejected.
- Silver artifact validity is proven via SHA-256 matching.

## 6. Light Curve Scientific Feature Engineering (`lc-features-v1`)

Phase 5.2 introduces deterministic feature engineering from `silver-lightcurve-v1` Parquet series.

### Feature Families
1. **Identity & Provenance**: `lineage_id`, `source_product_id`, `sample_id`, `tic_id`, `sector`, `feature_version`, `feature_fingerprint`.
2. **Quality & Time Coverage**: `n_points`, `time_min`, `time_max`, `time_span`, `median_cadence`, `max_gap`.
3. **Distribution & Variability**: `flux_mean`, `flux_median`, `flux_std` (`ddof=0`), `flux_mad`, `flux_robust_sigma` (`1.4826 * MAD`), `flux_amplitude` (`p95 - p05`), `flux_rms`, `flux_skewness` (`scipy.stats.skew`), `flux_kurtosis` (Fisher excess).

## 7. TPF & FFI Vetting Evidence Features (`tpf-vetting-v1`, `ffi-evidence-v1`)

Phase 5.3 introduces deterministic spatial and image evidence feature extractors from Silver Target Pixel (`silver-target-pixel-v1`) and Silver FFI (`silver-ffi-v1`) products.

### TPF Vetting Evidence (`tpf-vetting-v1`)
- **Normalized Pixel Photocenter Invariant**: Silver TPF pixels are normalized (`pixel / median - 1`). Classical absolute flux-weighted photocenter formula `sum(x * flux) / sum(flux)` is mathematically invalid. V1 computes **Transit Deficit Centroid** on nonnegative dimming maps (`max(out_median - in_median, 0)`).
- **Candidate Transit-Window Deficit Localization**: Consumes candidate ephemeris (`bls_period`, `bls_duration`, `bls_transit_time`) from `lc-features-v1` when paired via `sample_id` (and matching `tic_id`/`sector`).
- **Feature Families**:
  1. **Shape & Quality**: `n_cadences`, `rows`, `cols`, `pixel_count`, `finite_pixel_fraction`.
  2. **Temporal Variability**: `pixel_mad_median`, `pixel_mad_mean`, `pixel_mad_max`, `variability_peak_fraction`, `variability_effective_pixels`.
  3. **Summed Flux Variability**: `summed_flux_std`, `summed_flux_mad`, `summed_flux_p05`, `summed_flux_p95`.
  4. **Transit Deficit Evidence**: `transit_evidence_available`, `transit_in_cadences`, `transit_out_cadences`, `transit_deficit_sum`, `transit_deficit_peak_fraction`, `transit_deficit_effective_pixels`, `transit_deficit_centroid_row`, `transit_deficit_centroid_col`, `transit_deficit_center_offset_pixels`.

## 8. Catalog Enrichment & Label Versioning (`candidate-label-policy-v1`)

Phase 5.4 introduces immutable catalog snapshot integration (TIC, TOI, TCE) and candidate-level ephemeris matching (`toi-match-v1`).

### Core Invariants
1. **Catalog Snapshot Participation**: Gold snapshot manifests MUST reference exact immutable catalog snapshot IDs (`tic_snapshot_id`, `toi_snapshot_id`, `tce_snapshot_id`) and label snapshot IDs (`label_snapshot_id`).
2. **Signal Feature Independence**: Changing a TOI catalog disposition creates a new `label_snapshot_id` but leaves numerical signal features (`bls_period`, `bls_depth`, `flux_std`, `transit_deficit_centroid`) 100% untouched.
3. **Supervision Isolation**: Supervision metadata (`training_label`, `toi_disposition`, `matched_toi_id`) is strictly tagged and MUST NOT be included in model input feature allowlists during supervised training.

## 9. Gold Parquet Materialization & Feature Checkpoints (`gold-candidate-v1`, `gold-anomaly-v1`)

Phase 5.5 introduces durable, immutable Gold Parquet dataset materialization and crash recovery checkpoints under `checkpoints/feature-engineering/`.

### Core Invariants
1. **Manifest Commit Ordering**: A Gold snapshot is COMMITTED only when all sector Parquet files are uploaded and verified, followed by the upload of `gold/snapshots/<snapshot-id>/manifest.json`. Partial Parquet files without a committed manifest are ignored.
2. **Feature Engineering Recovery Checkpoint**: Build progress is tracked at `checkpoints/feature-engineering/snapshots/<snapshot-id>.json` across states `PLANNED` -> `MATERIALIZING` -> `DATA_STORED` -> `COMMITTED`. Crashes during materialization reuse already verified sector Parquet files without repeating feature extraction.
3. **PyArrow Explicit Schema & ZSTD Compression**: Parquet partitions are written using PyArrow with ZSTD compression and explicit schema coercion (converting missing values to `null` rather than zeros).
4. **Current Production Pointers**: Updating `gold/current/candidate.json` or `gold/current/anomaly.json` requires explicit CLI opt-in (`--set-current`).
